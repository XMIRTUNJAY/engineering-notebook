## Priya's Tuesday morning

She opens the dashboard: 3 flashcards due, "Liquid Clustering" flagged weak, recommended next: re-read + 5 practice questions, mock exam readiness 61%. No human tutor is awake. ## Step 1 — One number for "how well she knows it"

A recommendation is a weighted sum over measurable things. Real code from `backend/app/algorithms/mastery.py` (verbatim):

<CodeExample
  title="Weighted mastery with recency decay"
  file="backend/app/algorithms/mastery.py:15-78"
  what="Quiz accuracy, hard-difficulty coverage, practice completion, hands-on work, and freshness combine into a 0–1 score with a human level name."
  why="Fixed weights make scores explainable, and the recency term (half-life 14 days) models forgetting instead of pretending knowledge is permanent."
  tradeoff="Weights are judgment frozen in code, never A/B tested. Transparent-and-arbitrary beats learned-and-opaque — but only if you say so openly."
>
```python
quiz_accuracy = quiz_correct / quiz_total if quiz_total > 0 else 0.0
difficulty_coverage = len(difficulty_covered) / 5.0 if difficulty_covered else 0.0
practice_completion = practice_completed / practice_total if practice_total > 0 else 0.0
hands_on = 1.0 if hands_on_completed else 0.0
recency = math.exp(-days_ago / 14.0)   # half-life 14 days

score = (quiz_accuracy * 0.40 + difficulty_coverage * 0.25 +
         practice_completion * 0.15 + hands_on * 0.10 + recency * 0.10)
# <0.2 unknown, <0.4 recognition, <0.6 understanding,
# <0.8 application, <0.9 implementation, else troubleshooting
```
</CodeExample>

**Compute Priya's score with her:** 8/10 quiz (0.8), difficulties {3,4,5} (0.6), 6/8 practice (0.75), hands-on done (1.0), correct 7 days ago (e⁻⁰·⁵ ≈ 0.61). Score ≈ 0.32 + 0.15 + 0.1125 + 0.10 + 0.061 = **0.744 → "application"**. Notice the embedded teaching philosophy: hard things (0.25) outweigh many things (0.15). When you write scoring, the weights *are* the product philosophy — choose them deliberately, then test every level boundary (this repo does: 11 mastery tests).

Two senior details in the real file: the timezone guard (database returns aware timestamps, `utcnow()` is naive — a classic production crash, pre-empted in a comment), and the dual scale (0–1 here, 0–1000 in storage — know both before integrating).

## Step 2 — When she sees it again (SM-2)

```python
if quality < 3:
    interval_days, repetitions = 1, 0          # failed: tomorrow
    new_ease = max(1.3, ease_factor - 0.2)
else:
    if repetitions == 0: interval_days = 1
    elif repetitions == 1: interval_days = 6
    else: interval_days = round(interval_days * ease_factor)
    repetitions += 1
    new_ease = ease_factor + (0.1 - (5 - quality) * (0.08 + (5 - quality) * 0.02))
    new_ease = max(1.3, new_ease)
```

Mental model: each card carries *ease* (how well known) and *interval* (when to resurface). **Trace Priya's card with her:** quality=4, ease=2.5, interval=6, reps=2 → 15 days, ease 2.5, reps 3. Now quality=2 → tomorrow, ease taxed, reps reset. Two traces and you own the algorithm. Scope note: SM-2 schedules *recall* (flashcards), never *skill* — the engine correctly limits it there.

## Step 3 — What's weak, what's next, what path

One pattern, three applications — score candidates, rank, act:

```text
weakness = (1 - mastery) * 0.5 + error_rate * 0.3 + recent_share * 0.2
flag above 0.4 with typed reason + fix suggestion
recommendations = blend(goal .20, gap .15, weakness .15, forgetting .15,
                        prereqs .10, project .10, difficulty .05)
path = ancestors(target) minus mastered, depth-sorted
```

Path finding runs Kahn's topological sort that **raises on cycles** — a curriculum requiring A-before-B-before-A is broken by construction, and code should prove it. Fair exams come from stratified sampling (40/40/20 across difficulties, seeded shuffle: same seed, same paper). Every threshold is a named constant with a test.

## The content behind the math: a real trap

The engine reasons over curated confusions like this verbatim entry from `knowledge-base/exam_traps.yaml`:

> *"500 TB table, 3–4 query dimensions, partitioned by date, slow. What now?"* → Liquid Clustering on the most-filtered dimensions — with explicit reversals (need DROP PARTITION lifecycle → partitioning wins).
