- **Build your own:** Constraints → Architecture → The contract rule → Try the demo → The tutorial series → Exercises at the end.

> "It is not that we have a short time to live, but that we waste a great deal of it." — Seneca

Priya has one hour a day. That constraint shaped more of this system than any technology choice: every feature here exists to stop her hour from leaking — into deciding what to study, relearning what evaporated, or trusting a practice score that means nothing. The scheduling math, the fairness rules, the refusal to burn money on models at runtime all trace back to respecting sixty minutes.

## The spark

I kept watching the same failure: capable engineers studying for months and walking into exams unready — not from laziness, but because their tools answered none of the three questions that matter. What do I study next? What have I forgotten? Am I actually ready? A folder of PDFs answers none of them. A quiz app with random questions answers the third one dishonestly.

So the project began as those three questions, not as a stack. The stack came later, chosen to serve them: something that remembers (a database), something that schedules (memory science as arithmetic), something that tests fairly (sampling with rules). If you take one thing from this page, take the order — questions first, technology last.

## The struggle

Three things went wrong enough to leave marks. All three are still visible in the repo, which is the point.

**The math had no tests.** The 2025-09-01 audit found a study engine with zero test framework — scheduling logic deciding real mornings with nothing pinning it down. The fix was the engine split: six pure modules in `backend/app/algorithms/` plus 9 test files, 86 passing. The audit file is still in the repo. It reads uncomfortably. It should.

**The browser gave out rewards.** The app once trusted Priya's browser to award XP, and browsers can lie — to themselves (bugs) and for their owners (cheats). The `BUG-017` comment in `exams.py` records the day that ended: XP is awarded server-side on pass now. Forged progress also creates support tickets nobody can adjudicate, so this was never just about cheating.

**Demo data leaked into real shapes.** Test fixture rows were found sitting in production-shaped data. No user saw them, but the scare rewrote the discipline: seed and teardown are part of the test now, not decoration.

**Demo day broke the write path.** Registering live and answering one practice question surfaced two failures reads never would: the browser's answer and game-state calls die on CORS (`CORS_ORIGINS` defaults to empty), and the answer endpoint itself 500s with `MultipleResultsFound` — duplicate game-state rows behind a `get_or_create` with no unique constraint. Reads are end-to-end real; writes are backlog. Full field report: Part 6.

And one honest admission: the progress tracker faithfully records phases stalled for months. Process reveals stalling; it cannot cure it. That is not a failure of the system — it is the system telling the truth, which is all it promised.

## The decisions

<Decision
  title="Arithmetic recommendations instead of an LLM"

<Decision
  title="One Postgres for rows, vectors, and text"

| Decision | Option A | Option B | Chosen | Why |
| -------- | -------- | -------- | ------ | --- |
| Study brain | LLM suggestions | Fixed order | Deterministic math | Reproducible + free |
| Search | 3 systems | 1 Postgres | 1 Postgres | One person can run it |
| Reviews | Random | SM-2 schedule | SM-2 schedule | Memory science |
| Exam order | Pure random | Seeded shuffle | Seeded shuffle | Fair and re-checkable |

Neither table is universal advice. Each row holds only under this project's constraints: one operator, zero runtime model budget, fairness as a requirement. Change the constraints and the answers change — that is what makes them decisions rather than preferences.

## How it works

<TechStack items={['Python 3.11', 'FastAPI', 'PostgreSQL + pgvector', 'Redis', 'MinIO', 'SQLAlchemy 2', 'Alembic', 'Pytest', 'Next.js']} />

The whole system is one loop. Learn it once; the rest is detail:

```text
Priya answers a question
  ↓
The app records the attempt
  ↓
Mastery score is recalculated
  ↓
Weak topics are re-ranked
  ↓
Recommendations refresh
  ↓
Reviews are rescheduled
```

Six terms, explained once and never again:

- **API.** A menu of URLs. The screen orders; the backend cooks. `POST /exams/generate` means "cook me a new exam".
- **Database.** The notebook. Everything Priya did lives in Postgres: content, progress, history.
- **Spaced repetition (SM-2).** A scheduling recipe from memory science. Each flashcard carries difficulty and a waiting time; right answers stretch the wait, wrong ones shrink it.
- **Seeded shuffle.** Randomness with a fixed starting number. Same seed, same paper — a "random" exam that can be re-checked.
- **Vector search.** Finding by meaning: each concept gets 1024 numbers, similar meanings sit close, one indexed query finds neighbors.
- **Stratified sampling.** Dealing from marked decks — fixed shares per topic and difficulty, so no section hides.

Three chains connect requirements to what got built:

**Answers must be reproducible → models vary run to run → the study brain is arithmetic.** Six modules, 86 tests. Models draft content offline behind seven validators, never decide at runtime.

**One person operates it → every extra store is another 3 AM page → one Postgres.** Rows, vectors, keywords in one backup, one migration chain. Redis holds only temporary receipts.

**Content rots → messy syllabi in, broken lessons out → a 7-stage pipeline.** Ingest, extract, generate, validate, publish, index, vectorize — each stage checks the last one's work (the `JobType` steps in `backend/app/pipeline/orchestrator.py`).

  Exam answers must be reproducible and explainable. Every recommendation is arithmetic you can audit — same inputs, same outputs, free forever.
</Callout>

## The contract, then the code

The screen and the backend agree on promises before either is built. Three real ones from `backend/app/api/v1/exams.py`:

```bash
# Ask for an exam: certification in, fair paper out (70% to pass)
curl -X POST http://localhost:8000/api/v1/exams/generate \
  -H "Content-Type: application/json" \
  -d '{"certification": "databricks", "question_count": 20}'

# Hand it in: POST /exams/{exam_id}/submit → score + server-awarded XP
# Look back: GET /me/history → past attempts, newest first
```

Broken promises get honest codes: `400` malformed, `401` log in first, `429` slow down, `500` our bug. The shape never changes; only the data does.

Follow one submit end to end (module names real, from `backend/app/`): the exams router grades, `exam_service` records, XP lands server-side per BUG-017, `algorithms/mastery.py` recomputes, `weakness.py` re-ranks, `progress_service` persists to Postgres, and the dashboard reads fresh numbers next load. Handlers stay thin; thinking lives where tests run in milliseconds. That split is why the suite finishes in about four seconds.

Who remembers what: Postgres holds everything that matters (lose Redis and the system slows; lose Postgres and Priya's year is gone — back it up). Redis holds temporary receipts like idempotency keys. The browser holds nothing important, which is why closing a tab mid-exam costs nothing submitted.

## How AI was actually used here

The repo commits its own agent instructions (`AGENT.md`, `CLAUDE.md`), which is the honest version of "AI-assisted": the agent reads the same specs, ADRs, and layer rules a human teammate would. What gets delegated: implementation inside a reviewed plan, tests, validators, boilerplate. What doesn't: the decisions above, the weights, the fairness rules, the call on what ships.

Verification is mechanical, not hopeful: `make test-unit` must stay green, the layer rule is checked in review, new magic numbers need owners. One gap I'll name plainly: agent mistakes aren't logged anywhere — there is no record of what agents got wrong, so that particular lesson can't compound yet. The test suite catches the errors; the absence of a log means the *patterns* escape.

## Reflection

**What worked.** The maps survived a year — specs still describe the code. The engine split turned untestable math into 86 green tests. One store keeps the whole thing operable by one person.

**What didn't.** Fixture rows in production-shaped data (fixed with seed/teardown discipline). Client-awarded XP (fixed server-side). Answer writes failing live — CORS config plus duplicate game-state rows (open backlog, diagnosed). The tracker recording stalled phases nobody resumes (unfixed — process reveals, humans resume).

**What surprised me.** How much of "study app" turned out to be scheduling and sampling rather than content. The content matters least and breaks most — hence the pipeline getting the heaviest machinery.

**What I'd change.** Write the dimension contract before the first embedding lands (discovered, not designed). Collapse the duplicate flat/integration test layouts. Turn the progress tracker from honest record into weekly ritual.

**What remains unsolved.** Whether the mastery weights match reality — they are judgment, never calibrated against logged outcomes. That experiment is scoped and waiting: hypotheses first, numbers after.

## Build your own

Reproduce it exactly (`make install`, `dev-up`, `migrate`, `seed`, `test-unit` — 86 green is your checkpoint), then: change one SM-2 weight and watch Priya's Tuesday move; break one validator and see where bad content stops; ask an agent to add a feature using the repo's own instruction files, then review it like a skeptic; measure exam-generation latency for 60 questions and write the number down — it becomes the project's first performance fact.

Five things worth keeping: same inputs, same outputs — that is why the brain is math. Name the source of truth per concern. One store you can operate beats three you cannot. Validators are features, not overhead. Untested code is unteachable.
