## What

A mutual-fund intelligence platform for DIY Indian investors: import your CAS statement, get a consolidated portfolio, true cost of ownership (regular-vs-direct leakage in rupees), overlap detection, underperformance flags, tax-loss harvesting hints, and reconciled returns. Method-first: every formula lives in a versioned methodology doc before it lives in code.

## Why this shape

Three pressures: money math must be auditable (hence formulas in docs first, code second, golden portfolios always); Indian mutual-fund data is messy (CAS files, NAV histories, scheme mergers — hence a 4-strategy scheme mapper plus corrections pipeline); and trust is the product (hence PAN encryption, masked display, audit logs, and mission guardrails that permanently exclude rankings, affiliates, and ads).

<Callout type="decision" title="Why a modular monolith, not microservices">
  One deployable, strict internal boundaries (ADR-001). A solo/small team cannot operate distributed systems honestly — no network partitions to debug, no version skew across services — while DDD layers keep the code splittable later if scale ever demands it.
</Callout>

## Constraints

- Money math must be reproducible (methodology versions, golden portfolios).
- PAN must never appear in plaintext outside encryption (AES-256-GCM + masked display).
- Content pipeline must survive bad data (validators, dead-letter queue, corrections as rows).
- No execution, no rankings, no affiliates (mission guardrails, permanently excluded).
- Must run fully local via Compose (Postgres + Redis + MinIO).

## Engineering decisions

<Decision
  title="Frozen entities + value objects for money and identity"
  problem="Financial identity data (PAN) and money values must be valid everywhere, without checks scattered across handlers."
  options={["Validate inline at each use", "Value objects with validation in constructors", "Database constraints only"]}
  chosen="Frozen dataclasses + validating value objects (PAN regex + masking, Decimal percentages, ISIN/AMFI formats)."
  why="Invalid states become unrepresentable: a PAN object always holds a valid PAN, and __str__ returns the masked form so logs can't leak it."
  tradeoffs="More types to learn; conversion at every boundary. I would choose plain strings with validators only for throwaway scripts — never for identity or money."
  result="8 PAN tests, 10 crypto tests; leakage structurally impossible, not just discouraged."
/>

<Decision
  title="Golden portfolios as the money test suite"
  problem="Financial calculations need regression protection that unit tests of isolated functions can't give."
  options={["Unit tests only", "Golden end-to-end scenarios (GP-01…GP-24)", "Manual spreadsheet checks"]}
  chosen="24 golden scenarios: lump sums, SIPs, mergers, renames, duplicate uploads, out-of-order data, missing NAVs — each with expected holdings, lots, opportunities, and alerts."
  why="Money bugs hide in interactions (a merger during a SIP with a missing NAV day), and only full-scenario fixtures catch them."
  tradeoffs="Fixtures are heavy to author and brittle to methodology changes — hence methodology versioning, so old goldens stay pinned to old rules."
  result="The suite that would catch a formula regression before any user does."
/>

## What didn't work

Resolved, evidenced items only:

**Client-side anything for money.** Rewards and progress computed in the browser were gameable and unverifiable. Evidence: server-authoritative patterns throughout the backend plus audit logging on sensitive actions. Lesson: money decisions happen server-side, always.

**Single test style.** Unit tests alone missed interaction bugs (merger × SIP × missing NAV). Evidence: the golden suite GP-01…GP-24 plus property-test markers and a regression suite for two CAS formats. Lesson: match the test shape to the failure shape — money fails at intersections.
