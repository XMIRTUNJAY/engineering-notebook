> "We suffer more often in imagination than in reality." — Seneca, Letter 13 to Lucilius

Banking apps show balances; spreadsheets show formulas nobody audits; most planners show a single retirement number with false precision. All three ask you to imagine certainty where none exists. This project started from the opposite stance: make uncertainty visible — bands, not points — and derive every number from inputs a human can check.

## The spark

I wanted to answer a question my existing tools couldn't answer honestly: *where do I stand, and when can I stop?* A bank balance answers the first half for today and nothing else. A spreadsheet answers both halves until one formula rots silently — and spreadsheet rot is silent by design, which is what makes it dangerous for money. So the project began as a requirement, not a stack: monthly truth I record myself, math anyone can re-derive, and forecasts that show ranges instead of pretending to predict markets.

## The struggle

**The health score I couldn't explain.** The first version computed financial health from allocation heuristics — weights totaling 95, a goal component driven by milestone progress rather than goals. It looked mathematically reasonable and meant nothing I could defend. If you can't explain what a score means, the score is decoration. It was rebuilt as seven transparent sub-scores (liquidity, savings, debt, emergency, goals, diversification, history) weighting to exactly 100, with tests pinning the near-full and zero states.

**Math with no harness.** The audit found no test framework installed at all — money code running on hope. The fix was the `engine/` split: framework-free pure modules plus 9 vitest files, 40/40 passing. The lesson generalized across every project on this site: untested code isn't just risky, it's unteachable.

**Two brains, one truth.** Snapshots get recomputed on the server and re-derived in the client context. Two paths to the same number is a standing invitation to drift, and the audit flagged it as the top risk. It hasn't bitten. The parity between the two paths is the thing I would test next, before anything new.

  title="Snapshots as source of truth"

  result="Change decomposition (contributions vs growth) falls out for free; export/restore stays coherent."
/>

<Decision
  title="Seeded Monte Carlo bands instead of point forecasts"
  problem="Single-number projections pretend certainty the market never offers."
  options={["Deterministic compound projection only", "Monte Carlo with fixed seed", "Full stochastic model with fitted distributions"]}
  chosen="LCG + Box-Muller simulation, 1000 paths, p10/p50/p90 output, seed parameter."
  why="Seeded runs are bit-identical (measured), which makes statistical code unit-testable; bands communicate uncertainty honestly."
  tradeoffs="LCG quality is fine for projections, not cryptography; inflation input is computed but not yet wired into the path."
  result="~31 ms per run; UI recomputes per keystroke; tests assert exact outputs."
/>

<Callout type="decision" title="Why three databases">
  A single hosted database would violate the privacy constraint; localStorage-only would cap query power and durability. So: server SQLite with migrations, a browser IndexedDB mirror, and Postgres purely for opt-in sync. Three stores sounds like sprawl until you see each one defends a constraint the others can't.
</Callout>

Four constraints did the rest of the shaping, extracted from the implementation rather than aspired to: zero cloud dependency (Dexie mirror), privacy (SQLite file plus optional self-hosted sync), deterministic tested math (seeded engine), and Excel/CSV import for the messy reality of bank exports. Deployment stays one file plus one command.

The file to understand first is `local-bridge.ts`: every data request passes through it, and it routes each call either to the API routes (server mode) or to Dexie (local mode). One UI, two backends, zero rewritten components when switching. The file to understand second is `src/lib/engine/`: framework-free math — health, projections, scenarios — with no imports from the app, which is exactly why it can be tested in milliseconds and reasoned about on paper.

The monthly check-in wizard is where truth enters: per-asset values, once a month, becoming snapshots. Everything downstream — net worth, journey chart, runway, Monte Carlo bands, what-if scenarios — derives from those rows. Delete every derived table and the app rebuilds them; delete the snapshots and there is nothing. That asymmetry is the whole design.

## How help was used, and where judgment stayed

No agent workflow is recorded in this repo's history — no instruction files, no task reports — so the honest statement is that the judgment trail lives in the audit and the rebuild it triggered: foundation before features, engine split before new screens, tests before trust. The deterministic design is itself AI-era-proofing: seeded, pure, exactly-asserted math is checkable by anyone or anything, while the two-path drift risk above is precisely the kind of thing no agent would flag unprompted. Verification here is mechanical: 40 green tests, bit-identical seeds, screenshots from live runs.

## Reflection

**What worked.** Snapshots-as-truth survived contact with every feature — scenarios, export, forecasts all derive cleanly. Seeded randomness made statistics testable, which still feels like a trick worth stealing.

**What didn't.** Health v1 (a score I could not defend), untested math (fixed by the split), and the standing two-path drift risk (acknowledged, untested — the next test to write).

**What surprised me.** How little of a finance app is finance: most of the work is input plumbing, state sync, and import parsing. The money math is the small, dense center.

**What I'd change.** Wire inflation into the Monte Carlo paths; write the server/client parity test; then stop adding features until a real year of snapshots exists to learn from.
